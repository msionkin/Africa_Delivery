| CN.SEL.01 | Горизонтальное масштабирование | Способность приложения или каждого отдельного компонента системы масштабироваться горизонтально, увеличивая или уменьшая количество экземпляров процессов данного компонента отдельно от остальных компонентов, при этом распределяя нагрузку между всеми экземплярами компонента, и сохраняя выполнение нефункциональных требований ранее запущенными экземплярами компонента. | Все приложения и их компоненты должны поддерживать:<ul><li>запуск 2х и более экземпляров (реплик) приложения/компонента одновременно</li><li>параллельную работу 2х и более реплик</li><li>разделение входящей нагрузки между всеми репликами</li></ul>за исключением процессов:<ul><li>запускаемых периодически как Job, Cronjob</li><li>не влияющих на доступность системы</li></ul>Управление масштабированием в Kubernetes должно производиться через изменение количества реплик приложения/компонента в объектах конфигурации:<ul><li>[Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) - для прикладных компонентов</li><li>[StatefulSet](https://kubernetes.io/docs/concepts/workloads/controllers/statefulset/) - для stateful компонентов</li></ul>Разделение входящей нагрузки между репликами приложения/компонента в Kubernetes должно обеспечиваться встроенным механизмом [Service](https://kubernetes.io/docs/concepts/services-networking/service/) или стандартными средствами Service Mesh. | Обязательно, если применимо | 2 |
|   | **Отказоустойчивость** |   |   |   |   |
| CN.FTL.02 | Устойчивость к сбоям и автоматическое восстановление | Способность и готовность приложения и среды выполнения к автоматическому восстановлению работоспособности приложения после сбоев внутренних компонентов. | Для каждого приложения/компонента должно обеспечиваться:<ul><li>контроль количества одновременно запущенных реплик</li><li>контроль работоспособности каждой отдельной реплики</li></ul>В случае потери работоспособности отдельной реплики приложения, должен производиться автоматический перезапуск реплики.<br><br>Для приложений под управлением Kubernetes, данное требование должно реализовываться поддержкой стандартных интерфейсов проверки статуса на уровне контейнера:<ul><li>[Liveness probe](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) определяет что приложение находится в работоспособном состоянии. Контейнеры, не возвращающие положительный результат Liveness probe, автоматически перезапускаются платформой. Таким образом, "зависшие" реплики приложения возвращаются в работу, повышая уровень доступности приложения.</li><li>[Readiness probe](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) определяет что приложение готово к приёму трафика. Платформа подключит Pod к обработке внешних вызовов только после положительного ответа всех контейнеров на Readiness probe. Readiness probes используются приложениями для контроля корректной инициализации или регулярной проверки доступности внешних зависимостей, необходимых для работы. Pod'ы, не возвращающие положительный результат Liveness probe, исключаются из обработки трафика.</li><li>[Startup probe](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) используется для приложений с длительным временем загрузки, превышающим интервал проверки Liveness probe. Startup probe позволяет настраивать более гибкую логику проверки запуска приложения за счёт использования отдельных параметров startupProbe.failureThreshold и startupProbe.periodSeconds вместо одного параметра livenessProbe.initialDelaySeconds.</li></ul> | Обязательно | 1 |
